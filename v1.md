# Home Compute Harness — v0 MVP Plan

## 1. Purpose of v0

The purpose of v0 is **not** to build the complete distributed compute system.

v0 exists to prove that the fundamental harness architecture works.

At the end of v0, we should be able to:

> Install/run an agent on multiple devices, have them automatically connect to a central control plane, identify themselves, advertise their capabilities/resources, maintain communication, and exchange basic commands/messages through a common extensible protocol.

If this foundation works correctly, later versions should be able to add execution runtimes, schedulers, phones, cloud machines, sensors, storage systems, AI planners, and other capabilities **without redesigning the core architecture**.

---

# 2. Frozen Architectural Principle

The v0 implementation must continue following the architecture already defined.

The core rule remains:

> **The Harness Core must not depend on a specific operating system, device type, transport mechanism, runtime, or future capability.**

The system should reason about:

- Nodes
- Resources
- Capabilities
- Transports
- Messages
- State
- Events

rather than directly reasoning about:

- Windows laptops
- Android phones
- Raspberry Pis
- Wi-Fi devices
- GPUs
- Smart fridges

Those become implementations or extensions of the generic concepts.

---

# 3. v0 Scope

v0 will consist of:

```text
                    HARNESS MANAGER
                         │
                         │
                Local Network / LAN
                         │
              ┌──────────┼──────────┐
              │          │          │
           Agent A    Agent B    Agent C
           Laptop     Desktop     Laptop
```

For the first version, the target environment should be intentionally simple:

- One central manager
- 2–3 computers
- Same local network
- Windows/Linux/macOS where practical
- One common node agent
- Persistent node identity
- Node discovery
- Registration
- Heartbeats
- Resource/capability reporting
- Two-way communication
- Basic command/message exchange
- Node state tracking
- Basic event system
- Simple dashboard or CLI visibility

No real distributed workload execution is required yet.

---

# 4. What v0 Must Demonstrate

The MVP should prove six fundamental things.

## 4.1 Device Discovery

A new agent running on the home network should be capable of finding the Harness Manager.

Example:

```text
Laptop starts Agent
        ↓
Agent discovers Manager
        ↓
Agent requests connection
```

For v0, discovery can operate only within the local network.

The discovery mechanism should remain abstracted behind a transport/discovery interface so that later we can introduce:

- Internet-based discovery
- Mesh networking
- Bluetooth gateways
- Cloud relays
- Manual pairing
- QR-code pairing

without changing node logic.

---

## 4.2 Device Registration and Identity

Every participating device becomes a **Node**.

Example:

```text
Node ID:
node-a8f21

Name:
Ashutosh-Laptop

Platform:
Windows

Architecture:
x86_64
```

The node must have an identity that does not depend on its IP address.

Changing from:

```text
192.168.1.23
```

to:

```text
192.168.1.64
```

must not cause the harness to think it is a new device.

v0 therefore needs:

- Persistent Node ID
- Node metadata
- Basic identity credentials
- Registration lifecycle

---

# 5. Node Manifest

Every node should publish a generic manifest.

Conceptually:

```text
Node
│
├── Identity
├── Metadata
├── Resources
├── Capabilities
├── Runtime Support
└── Current State
```

Example information:

```text
Node

Identity
  node-id
  hostname

Platform
  operating system
  architecture

Resources
  CPU
  memory
  storage

Capabilities
  system.execute
  filesystem.read
  filesystem.write

State
  online
  CPU utilization
  available memory
  uptime
```

The schema must be extensible.

Later we should be able to add:

```text
GPU
NPU
camera
microphone
battery
Bluetooth
location
temperature sensor
Docker
WASM
AI accelerator
```

without redesigning the node representation.

---

# 6. Connection Lifecycle

Every node should follow a well-defined lifecycle.

```text
UNKNOWN
   │
   ▼
DISCOVERED
   │
   ▼
REGISTERING
   │
   ▼
CONNECTED
   │
   ▼
READY
   │
   ├─────────────┐
   │             │
   ▼             ▼
DEGRADED       OFFLINE
                 │
                 ▼
             RECONNECTING
```

The manager should always know the current state of each node.

---

# 7. Heartbeat System

Nodes periodically communicate their health to the manager.

Example:

```text
Agent
  │
  │ heartbeat
  ▼
Manager

"I'm alive."
```

The heartbeat may contain:

- Node ID
- Current timestamp
- CPU usage
- Memory availability
- Current health
- Agent version

The manager uses heartbeat expiry to determine whether a node has disappeared.

Example:

```text
14:20:10 heartbeat
14:20:15 heartbeat
14:20:20 heartbeat
        ↓
connection lost
        ↓
timeout
        ↓
NODE_OFFLINE
```

This mechanism later becomes fundamental for workload reassignment.

---

# 8. Communication Protocol

v0 should define the first version of the **Harness Protocol**.

The protocol should be independent of the actual transport underneath it.

Conceptually:

```text
Harness Message
│
├── Message ID
├── Protocol Version
├── Message Type
├── Source Node
├── Destination
├── Timestamp
└── Payload
```

Initial message types can include:

```text
DISCOVER
REGISTER
REGISTER_ACK
HEARTBEAT
STATE_UPDATE
CAPABILITY_UPDATE
COMMAND
COMMAND_RESULT
PING
PONG
ERROR
```

The important part is establishing the envelope and versioning model now.

Later we should be able to add:

```text
WORKLOAD_ASSIGN
WORKLOAD_CANCEL
STREAM_OPEN
FILE_TRANSFER
SERVICE_DEPLOY
CAPABILITY_INVOKE
POLICY_UPDATE
```

without replacing the protocol.

---

# 9. Two-Way Communication

The manager must not simply receive information from agents.

Both sides should be capable of initiating messages.

Example:

```text
Agent → Manager

HEARTBEAT
RESOURCE_UPDATE
EVENT
```

and:

```text
Manager → Agent

PING
REQUEST_STATE
COMMAND
```

This proves that the harness can eventually support actual workload orchestration.

---

# 10. Basic Command Model

v0 should contain a harmless generic command mechanism purely to demonstrate communication.

Examples:

```text
PING

GET_SYSTEM_INFO

GET_AGENT_STATUS

ECHO "hello"

REQUEST_RESOURCE_REFRESH
```

The purpose is not remote shell execution.

The purpose is to prove:

```text
Manager
   ↓
Command
   ↓
Agent
   ↓
Execution
   ↓
Result
   ↓
Manager
```

This becomes the foundation of future workload execution.

---

# 11. Resource Registry

The manager maintains an internal **Resource Registry**.

Example:

```text
Harness

Nodes: 3

Node A
CPU      8 cores
RAM      16 GB
Storage  200 GB

Node B
CPU      16 cores
RAM      32 GB
Storage  1 TB

Node C
CPU      8 cores
RAM      8 GB
Storage  70 GB
```

The registry should expose queries like:

```text
List nodes

Get node

List node resources

List node capabilities

Get node health
```

Later the scheduler will operate entirely on this resource registry.

---

# 12. Event System

v0 should establish an internal event model immediately.

Important initial events:

```text
node.discovered

node.registered

node.connected

node.ready

node.updated

node.offline

node.reconnected

command.sent

command.completed

command.failed
```

Architecture:

```text
Agent
   ↓
Node disconnects
   ↓
Manager
   ↓
NODE_OFFLINE event
   ↓
Event Bus
   ├── Resource Registry
   ├── Logging
   ├── UI
   └── Future Scheduler
```

The future scheduler should therefore not need to be tightly coupled to networking code.

---

# 13. State Store

v0 should distinguish between:

### Runtime state

Fast-changing information:

```text
online status
CPU load
RAM usage
last heartbeat
connection state
```

### Persistent state

Information that should survive manager restart:

```text
Node identity
Node name
registration information
trusted devices
known capabilities
configuration
```

Even if v0 initially uses a simple local database, these concepts should remain separated.

This makes it possible to introduce distributed control-plane storage later.

---

# 14. Transport Abstraction

For v0 we can use one transport implementation.

For example:

```text
LAN
 +
WebSocket / QUIC / gRPC
```

But the system must expose it conceptually as:

```text
Transport
```

rather than:

```text
WebSocket everywhere in the codebase
```

Future transports might include:

```text
LocalTransport

MeshTransport

InternetRelayTransport

BluetoothGatewayTransport

CloudTransport
```

All of them should carry the same Harness Protocol.

---

# 15. Manager Responsibilities

The v0 Manager should handle:

```text
Discovery
Registration
Authentication
Connections
Heartbeats
Node Registry
Resource Registry
Capability Registry
Messaging
Command Dispatch
Event Generation
State Persistence
Basic API
```

It should **not yet handle**:

```text
Complex scheduling
Distributed workload execution
AI planning
Container orchestration
Distributed storage
High availability
Cloud bursting
```

Those belong to later versions.

---

# 16. Agent Responsibilities

Every node agent should handle:

```text
Generate/load identity

Discover Manager

Register with Manager

Maintain connection

Send heartbeats

Collect system information

Publish resource manifest

Publish capability manifest

Receive protocol messages

Execute supported basic commands

Return results

Reconnect after network failure
```

The agent should expose extensions internally so that later we can plug in:

```text
WASM runtime

Docker runtime

GPU capability

Camera capability

Bluetooth capability

Storage capability
```

without rebuilding the entire agent architecture.

---

# 18. v0 Demo Scenario

The final MVP demonstration should be extremely clear.

### Step 1

Start Manager on Computer A.

```text
Harness Manager
ONLINE
```

### Step 2

Start Agent on Computer B.

Agent discovers Manager.

```text
New Node Discovered
```

### Step 3

Node registers.

```text
Laptop-B
REGISTERED
```

### Step 4

Start another Agent on Computer C.

Manager now shows:

```text
3 Nodes

Manager-PC
Laptop-B
Desktop-C
```

### Step 5

Each device reports resources.

```text
Total visible resources

CPU        32 cores
Memory     56 GB
Storage    1.4 TB
```

This number is only informational in v0.

No pooled execution yet.

### Step 6

Manager sends:

```text
PING
```

to Laptop-B.

Laptop responds:

```text
PONG
Latency: X ms
```

### Step 7

Manager sends:

```text
GET_SYSTEM_INFO
```

Laptop replies.

### Step 8

Disconnect Laptop-B from Wi-Fi.

Manager detects:

```text
Laptop-B
OFFLINE
```

and emits:

```text
node.offline
```

### Step 9

Reconnect the laptop.

The same Node ID returns:

```text
Laptop-B
RECONNECTED
```

No duplicate node gets created.

If these flows work reliably, v0 has succeeded.

- Smart fridge support
- Bluetooth devices

- Distributed storage

## Milestone 0 — Core Contracts

Freeze definitions for:

```text
Node
Resource
Capability
Message
Transport
Command
Event
NodeState
```

---

## Milestone 1 — Manager Skeleton

Build the control-plane foundation:

```text
Manager startup
Configuration
Node registry
State store
Event bus
API layer
```

Deliverable:

Manager runs independently with no agents connected.

---

## Milestone 2 — Agent Skeleton

Build a portable node agent.

Agent can:

```text
start
generate identity
collect system metadata
maintain local configuration
```

Deliverable:

Same agent architecture running on at least two computer platforms.

---

## Milestone 3 — Discovery & Pairing

Implement:

```text
Manager discovery
Agent registration

```

Deliverable:

Agent can join the harness without manually configuring IP addresses.

---

## Milestone 4 — Persistent Connection

Implement:

```text
connection establishment
reconnection
heartbeat

```

Deliverable:

---

Agents publish:

```text

```

---

# 21. Definition of Done

v0 is considered complete when all of the following work reliably:

- Multiple devices can participate.
- Devices can discover the manager.
- Devices receive persistent identities.
- Devices can register.
- Manager tracks online/offline state.
- Agents reconnect automatically.
- Resource information is reported.
- Capability manifests are reported.
- Manager can communicate with any node.
- Nodes can return structured responses.
- Internal events are emitted.
- State survives manager restart where appropriate.
- Protocol messages are versioned.
- Core concepts contain no device-specific assumptions.
- Adding a future transport/runtime/capability does not require redesigning the core domain model.

---

# 22. What v0 Unlocks

Once v0 exists, the next layer becomes much easier.

```text
v0
Connectivity + Identity + Resources + Communication

                    ↓

v1
Actual workload execution

                    ↓

v2
Scheduling + resource-aware placement

                    ↓

v3
Services + desired-state reconciliation

                    ↓

v4
Phones + edge devices + capability invocation

                    ↓

v5
Mesh networking + remote devices

                    ↓

v6
AI intent planner

                    ↓

Personal Distributed Compute Operating System
```

The key objective of v0 is therefore not impressive compute performance.

It is to establish a **small, boring, reliable and extensible harness foundation** on which every future capability can be added.
