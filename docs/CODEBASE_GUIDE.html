Home Harness

A way to use every computer and phone you own as one pool of compute. One manager hands work to agents running on your devices, over an authenticated, certificate-pinned connection. Written in Go (about 40,000 lines plus tests) with a small Java Android app. Everything is typed, allow-listed and device-agnostic.

1. What it is

  • Manager: one program (on a PC or phone) that knows every device, decides where work runs, and serves a dashboard and an API on 127.0.0.1:7421.
  • Agent: a small program on each device (Windows, Linux, macOS, Android). It connects to the manager, reports what the device can do, and runs the tasks it is given.
  • Tasks are not arbitrary commands. They are typed catalog tasks (resize an image, ask a local AI model, hash files, run a container...) with a schema the manager checks and the agent re-checks. Raw commands exist but are off by default.
  • Jobs run one task per file across the fleet and combine the results. Workflows chain stages. The AI planner turns a sentence into a checked plan that only runs when you approve it.
The one rule: the manager never trusts what an agent, an AI model or a remote relay says. They propose; the manager checks every request against the catalog, policy and the operator's credentials before anything happens.

2. Architecture

  • Transport: agents open a WebSocket to the manager over TLS. They pin the manager's certificate fingerprint (P-256) instead of trusting a CA.
  • Joining: by a pairing token, a one-time invitation (QR or link), or by approval: the device shows a 6-digit code that also appears on the manager.
  • State: a bbolt database (devices, jobs, workflows, audit, policy...). Files (task inputs and outputs) are a content-addressed store keyed by SHA-256.
  • Events: an in-memory bus feeds the dashboard's live updates (server-sent events over an authenticated fetch).

3. Life of a task

  1. You submit (dashboard, harnessctl, API, or the AI planner after approval). Files are uploaded first and referred to by hash.
  2. The manager compiles the request against the catalog: required parameters, ranges, allowed values, file counts and extensions, policy (is this type enabled? which devices?).
  3. Placement picks a device that has the capability, the model or tool needed, free slots and memory, and is allowed to take work now (not on battery, not paused, within hours). Among equals: least busy first, then the device already holding the input files, then most free memory. If nothing has room right now the task is queued (priority, then age).
  4. The agent downloads the inputs (or copies them from its cache), runs the handler in its own work folder, streams progress, and uploads the outputs.
  5. The manager records the result. Jobs derive their state from their attempts, retry on other devices, and run the combine step when every task is done.

4. Trust and security

BoundaryHow it is protected
Agent to managerTLS with a pinned fingerprint; each agent has its own key pair; admission by token, invitation, or approved code; revocation list.
You to managerOperator bearer token (or a derived dashboard session). No cookies, ever. CSRF and DNS-rebinding guard. The AI key works only on /v1.
What runsTyped catalog + policy. Raw commands, container tasks and some types are off until you enable them. The AI planner can only propose catalog types.
Agent outputUntrusted: names, hashes, cache reports and results are validated; the dashboard escapes everything an agent or model wrote.
Wrong resultsOptional spot-checks re-run a sample of deterministic tasks on a different device and flag a device whose results differ.
BuildsSigned release manifest (Ed25519) checked before install; optional Windows/macOS code signing; the Android app updates only from its own signing key.
AuditSecurity-relevant actions are recorded (who, what, never the content of prompts or secrets).

7. Agent internals (internal/agent)

  • Connection loop: discover or dial the manager (or a known standby), register with a manifest (hardware, capabilities, features), heartbeat every few seconds with live CPU/memory/battery.
  • Workloads: receive an assignment, fetch inputs (verifying SHA-256, using a size-capped local cache), run the typed handler or command with limits, stream output, upload declared outputs.
  • Capabilities: re-probed every 30 seconds (is Ollama up, which models, which tools found) and sent to the manager when they change.
  • Self-update: on PCs the agent downloads and swaps its own binary (hash checked). On Android the app downloads the new app and installs it.
  • Split models, tunnels, failover: helper processes for llama.cpp, byte tunnels, and following a standby manager.

9. The Android app

  • Two modes in one APK: manager (runs the manager as a foreground service and shows the dashboard in a WebView) or worker (runs the agent, joins by approval).
  • The Go binaries ship as native libraries (Android only runs files from its install folder).
  • Self-update: the manager serves its own APK; the agent reports which APK it runs, downloads a newer one when told, and AppUpdater installs it with PackageInstaller. After the owner allows installs once, later updates need no taps (Android 12+).

10. Tests and builds

  • About 150 test files. Unit tests sit next to the code; integration tests in test/integration start a real manager and real agents in one process on 127.0.0.1 ports.
  • External tools (llama.cpp, ffmpeg, docker...) are tested with small stand-in programs that record the exact arguments they receive.
  • Key logic is mutation-checked: deliberately broken to confirm a test fails.
  • Builds: scripts/build-agents.sh (all platforms), build-windows-manager.sh (the installable bundle, with a signed manifest), build-android-app.sh (the APK).

11. Features: core platform

  • Multi-platform agents and self-update; revocation; operator authentication; fleet names and labels; audit log; host de-duplication.
  • Join by approval code, timed "add devices" window, invitations/QR; Windows manager install bundle with a watchdog; live fleet view.
  • Device availability: per-device rules (auto, always, idle, charging, paused, hours); work waits with a stated reason; keep-awake while working; below-normal priority.
  • Capacity slots per device, a FIFO-by-priority queue with aging, workload files (content-addressed), retention of old records.

12. Features: local AI

  • Local models through each device's Ollama; model management per device from the dashboard; GPU awareness.
  • OpenAI-compatible API (/v1/chat/completions, /v1/models, streaming) so any AI app can use your fleet with its own key.
  • Split models: one model too big for any device runs across several with llama.cpp through authenticated tunnels.
  • Batch AI: summarise, classify or embed a folder across devices and collect one report.
  • AI planner: a sentence and your files become a checked plan (optionally multi-step); it runs only on your approval.

13. Features: jobs, workflows, placement

  • Jobs: one task per file, spread over devices, retried elsewhere on failure, with a combine step.
  • Workflows: up to 8 stages in order; each stage works on the previous stage's results; checked completely before anything runs; survives a manager restart.
  • Placement: least busy first, then data already on the device (input cache), then memory. Priorities (high/normal/low) with aging.

14. Features: trust, failover, remote access

  • Spot checks (off by default): re-run a sample of deterministic tasks on another device; flag the odd one out.
  • Standby manager: a warm copy with the same identity; promote by hand (or automatically); a term number stops a returning old manager from acting as a second boss.
  • Remote dashboard (off by default): use the dashboard away from home through the relay with a separate key; every call is sealed so the relay cannot read, replay or change it; modes read-only, standard, full.
  • Signed builds: signed release manifest always; Windows Authenticode and macOS notarisation when you have the certificates.

15. Features: more task types

  • Image upscaling (built in); video/audio conversion, speech to text, PDF/photo text (switch on when the tool is installed); container tasks (Docker/Podman, allow-listed images, off by default).

16. Run and deploy

# build everything
bash scripts/build-agents.sh
bash scripts/build-android-app.sh
bash scripts/build-windows-manager.sh        # -> dist/windows-manager

# install or update the manager on this PC (keeps its state)
powershell -File dist/windows-manager/install.ps1 -InstallDir "%USERPROFILE%\.home-harness\laptop-manager" -NoDashboard

# talk to it
harnessctl nodes | models | tasks | jobs | workflows | plan "..." | policy | standby | remote
harnessctl update <node-id>               # PCs and the phone (the app updates itself)

Dashboard: http://127.0.0.1:7421 on the manager's machine (sign-in link printed by the installer). Live view: /live.
